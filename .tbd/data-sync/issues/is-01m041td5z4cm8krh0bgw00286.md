Measured on a 250k-file root while the walker was still scanning (2026-08-15):

- GET /api/rollup?path=&depth=0 took 2.6-5.4s REPEATEDLY (server log 'slow server request'), re-issued on each inventory-change event.
- A cold /api/kpress/render of a README took 1195ms; resource timing showed stalledBeforeRequest=30ms and serverThink=1160ms, so it is NOT browser connection queueing or the subtree prefetch - the server itself is slow to answer while the walker runs.
- Warm (kpress render cache hit) was 29ms, and cold renders of other files were 318-817ms, so it is not one-time process warmup either.

Diagnosis: foreground request handlers share CPU with the background inventory walker and rollup aggregation. They all run via asyncio.to_thread, so under the GIL a CPU-bound Python render competes with the walker rather than preempting it. Opening a single file is starved by work the reader did not ask for.

Direction (per Joshua): crawl breadth-first and show what is known immediately, refining as depth arrives, rather than making a folder view wait on a complete deep scan. Consider also prioritizing foreground request handlers over background scan work.

Relates to the 'Everything is effortlessly fast' principle in docs/design-system.md.
