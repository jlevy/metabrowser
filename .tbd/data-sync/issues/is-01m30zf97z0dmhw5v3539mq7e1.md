Found by an AST scan plus caller tracing while fixing mb-5721. (1) repository_store.py:128 store_lease takes a blocking flock directly inside async def lease_revision. Moving it to a worker thread changes which thread owns the lease, which changes what held_locks() and store_maintenance_lock report in-process (tests/test_git_revision_lease.py depends on the current ownership, expecting LockOrderError 'other mode' rather than LockBusyError) and touches the frozen acquire_shared transition in tests/fixtures/repository-cache/state-machines.json. Needs a decision on where lease ownership lives. (2) acquire.py:813 publish_from_staging and :807 open_cache are called straight from async def acquire_file_source with no to_thread; both are fully synchronous so the order check is sound, but they take blocking store_lease, repository_store_lock, source_alias_lock and the home lock, and open_cache also runs reclaim including rmtree, all on the event loop. Latent today because both paths are reached only from the CLI once at startup, before serving; if acquisition ever moves onto a request path the whole call belongs in asyncio.to_thread.
