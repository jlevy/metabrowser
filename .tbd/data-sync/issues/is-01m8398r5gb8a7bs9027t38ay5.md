Before T5 fixes its loading behavior, measure in headless Chrome (not the hidden browser
pane) on the 1,031-file comparison used for review of #284 and on a small one:

- the narrowed comparison route's server time and transfer, cold and cached;
- remounting the file list for a narrowed answer, through first screen;
- the same when the narrowed answer was prefetched on hover/focus of a menu row.

Target: no visible spinner, and under about 50 ms to a drawn first screen for a cached
or prefetched answer (the "effortlessly fast" principle). Record the numbers beside the
constant or prefetch decision they set. If a refetch cannot meet the target, bring the
measurements back to the epic before choosing another design.

## Notes

2026-11-22, not yet measured: the machine sat at a load average of 380 to 480, so no timing from it is a measurement. T5 (#742) landed first, at the user's direction to implement end to end. Findings so far, from the server's phases log on this repository served as a folder: a 150-commit first-parent range (1,496 files) answered whole in 7.1 s, view=types in 5.8 s, types=.md in 7.5 s and again in 15.8 s, all in the git phase. A served folder's comparison is never kept (comparison_cache_key is None for a working tree, whose answer can change), so on a folder every switch reruns the listing and hydration; on a store (a pin, a mirror, a pull request) the listing is kept and the answer bodies are immutable for build+store addresses, so a switch hydrates only the kept files and a repeat is the browser cache's. Still to do on a quiet machine, in headless Chrome: the 1,031-file comparison and a small one, cold and cached, and whether prefetching a row's answer on hover or focus reaches the 50 ms target; then decide whether the folder case needs a kept listing.
