Seen once by the #614 author at load average 46: tests/test_ref_selector_long_list_chrome.py's End step read the list as scrolled to the top while the foot rows were drawn. Three reruns did not reproduce. Precautions added in #614 (overflow-anchor: none on the list; focus the first row with preventScroll and wait a frame before End), cause unknown. Watch CI for recurrences; if it recurs, capture scrollTop over frames after End.

## Notes

2026-11-19: recurred in CI on #620's first run (chrome 3.13 2/4, tests/test_ref_selector_long_list_chrome.py:184, end inView is True); #620 touched no browser code; passed on rerun. So the precautions in #614 did not remove it.

2026-11-19: cause found, a product bug. renderNavFilterBar (app.js) rebuilds the Files toolbar with innerHTML and prepends the ref chooser back; Chrome drops the scroll position of an element taken out of the page, with no scroll event, so drawWindow never ran: the list read scrollTop 0 with rows 1970-2001 drawn and focus on 2001. The rebuild runs on every tally change: the root-summary refresh while the index warms up (late under load) and any file change in a live checkout. Reproduced deterministically (renderNavFilterBar() right after End: 57709 -> 0) and naturally (write a file after End, page's own fetchRootSummary redraw: main 6/6 fail, fix 6/6 pass). Fix in PR #625: drawWindow records rows.drawnAt; the refill observer (keepFocusAcross renamed keepAcrossRefills) restores it via keepScroll before focus. Rebuilding around the chooser in app.js went 190 bytes over the startup-script budget, so the fix is in the on-demand module. Test now redraws the toolbar after End deterministically; #614's guesses (frame/preventScroll before End, overflow-anchor: none) removed. 32/32 real-test runs at load 28-61 with the fix, 0 failures.
