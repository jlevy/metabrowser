src/metabrowser/static/git-panel.js:997 passes historyScroller().scrollTop straight into virtualWindow.read(), and :999 / :1100 / :1122 / :1810 write a window-computed scrollTop back. The window's arithmetic (git-history-window.js maybeRebase/read: logicalTop = segmentStart + floor(boundedScrollTop / rowHeight)) is relative to .git-graph-list, whose top is NOT the scroller's origin.

PR #86 shipped panel.replaceChildren(list) at 3ad9113, so the list WAS the first child and the two coordinate spaces agreed. The Git header tally (17ab718) changed it to panel.replaceChildren(summary, list) with .git-history-summary in normal flow (styles.css:4727 — display:flex, padding 6px 12px, border-bottom, min-height calc(1.5*var(--nav-font-size)+13px)), so scrollTop now includes roughly one row of header the window does not know about.

Impact, traced statically and NOT yet observed in a browser: row mapping is off by about one row, which the 64-row overscan absorbs, so normal scrolling still shows correct content. The visible risk is the scrollTop write-backs — segment rebase at the edges and rebaseToOrdinal for direct-route restoration and keyboard boundary navigation — which land about one row off target.

Fix (pick one): (a) give .git-graph-list its own scroll container so the window's origin assumption is structurally true; or (b) have git-panel.js convert between the two spaces at the boundary, subtracting the list's offsetTop within the scroller before read() and adding it back before any scrollTop assignment. Either way, state the contract in the git-history-window.js module docstring — it reads as a pure module accepting any coordinate space, and it is not.

Verification: scroll deep into a 10,000-commit corpus, force a rebase, and assert the ordinal at the viewport top matches the ordinal the window reports.
