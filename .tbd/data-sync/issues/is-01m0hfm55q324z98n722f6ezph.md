PR #59 was validated with throwaway scripts. Those measurements should be reproducible
on demand, so a later change to the walker, the aggregate cache, or the delivery layer
can be compared against a known baseline instead of re-argued.

One harness, two halves, one report.

Server side, from the CLI:

- Cold scan wall-clock with no client attached, which is walker throughput alone.
- Scan wall-clock with a client attached. This is the number that regressed before:
  rollup work and the walker compete for the GIL, so it is not the cold number.
- Time from server start to the first usable folder count on the wire.
- Rollup latency during the scan as a distribution (p50, p95, max), not a mean.
- Settled-index rollup split into its three real paths, reported separately: cold body,
  retained body, and 304 revalidation.
- /api/tree at the root versus at a subtree, reported against response size, so a cost
  proportional to the index shows up as one.
- N identical clients, both simultaneous and staggered.

Browser side: measured in a real browser against the same tree, because the client's own
coalescing and cache behavior is not visible from curl. Tracked separately.

Reporting: emit JSON so two runs can be diffed, plus a short human-readable table. Take
the tree size and a run label as arguments rather than hardcoding a corpus, and generate
the corpus as part of the run.

Measured while validating PR #59 on a 400k-file tree, as an example of the spread the
harness has to be able to show (Apple Silicon, APFS, warm page cache):

- Scan with a client attached: main did not finish, reaching 393,872 of 400,000 files at
  a 300s cutoff; PR #59 finished in 37.4s.
- Rollup p50 during the scan: 181ms on main, 6ms on PR #59.
- Rollup p95 during the scan: 347ms on main, 34ms on PR #59.

Suggested home is devtools/, matching the other repo-only tools, so it stays out of the
built wheel.

## Notes

Implemented as devtools/bench_serving.py, with the in-page half in
devtools/bench_browser_probe.js (printed by --browser-probe). Corpus, logs, and result
JSON land in .bench/, which is gitignored.

Both halves have been run against the branch and against main on the same machine and
the same corpus, and both surfaced real findings rather than just producing numbers.

Server side, 100,000 files, 972 directories, Apple Silicon and APFS:

                                            main    branch    change
  cold scan, walker only (ms)               2484      2388    unchanged
  scan with a client attached (s)           52.4       5.2    10.1x
  first folder count on the wire (s)        1.27      0.81     1.6x
  rollup during scan p50 (ms)               16.1       3.5     4.6x
  rollup during scan p95 (ms)               66.5       5.3    12.5x
  settled rollup, aggregated p50 (ms)       57.3       3.4    16.9x
  settled rollup, retained body p50 (ms)      57         3    19.0x
  settled rollup, 304 p50 (ms)                --       2.8    new path
  8 clients staggered p50 (ms)              48.7       3.4    14.3x
  8 clients simultaneous p50 (ms)          302.6      10.1    30.0x
  /api/tree root depth=1 p50 (ms)          501.1     516.1    unchanged
  /api/tree top00 depth=2 p50 (ms)          13.3       3.5     3.8x

Three of those rows are worth more than their ratios.

The cold scan is unchanged, which is correct and worth keeping visible: the walker does
the same work, and what changed is that it no longer competes with per-request
rescans. Reporting the attached scan separately is what makes that legible.

On main, "retained body" costs the same as "aggregated" (57ms against 57.3ms), because
there is no retained body -- every request aggregates again. The 304 row is absent
entirely. Splitting the three paths is what shows that, where one blended latency would
not.

The root tree request is unchanged at about 500ms, against a 3.8KB response, while a
123KB subtree response costs 6.4ms. Reporting latency against response size is what
makes that visible as a cost proportional to something other than the answer. See
mb-bb8v.

Browser side, from the probe on a settled 400k index: validators confirmed working
(304 with an empty body, stable ETag), and per-shape verdicts that distinguish
coalescing from the retained body rather than conflating them. It also quantified
mb-bb8v from the client's side -- 8 tabs on the root nav request cost 8.5s each and
68s of total server work, because that route has neither a validator nor a shared
build.

Follow-on ideas, none blocking:
- A --phase flag, so re-measuring one number does not re-run the whole thing.
- Wire the probe in automatically rather than serving it from the corpus by hand.
