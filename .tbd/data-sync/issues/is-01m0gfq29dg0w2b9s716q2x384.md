Identical concurrent rollup requests each run their own aggregation. Measured on
a settled 100k index: 1 request 30ms, 2 -> 57ms, 4 -> 107ms, 8 -> 236ms.

An ETag (mb-l8oy) removes the repeat cost for a client that already has the
answer, but not the first-time stampede: N clients arriving together on a folder
none of them has cached, or all of them refreshing after the same inventory
change, still do N aggregations of the same thing.

Single-flight keyed on the same (generation, path, options) tuple the ETag uses:
the first request computes, the rest await that result.

Care: the shared future must be dropped once the generation moves, or a late
joiner receives a result computed against an index that has since changed. The
subtree-aggregate memo already makes each computation cheap, so this is about
removing redundant work, not about making one computation faster.
